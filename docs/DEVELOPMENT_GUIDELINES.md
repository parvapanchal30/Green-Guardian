# Development Guidelines

## Workflow
UNDERSTAND → PLAN → DESIGN → IMPLEMENT → TEST → REVIEW → DOCUMENT. Small, reversible increments. Inspect a subsystem's dependencies before changing it. Evaluate existing deps before adding a library. Document tradeoffs before changing architecture.

## Documentation rule
When an important architectural/product decision is made: implement it → update the relevant doc → add a `DECISION_LOG.md` entry. Update `CURRENT_STATE.md` and `TODO.md` at the end of every working session. Code and docs must not diverge.

## Backend
- Python 3.12+, fully typed (`mypy --strict` on `app/`), `ruff` for lint/format.
- Layers: router → service → repository. No ORM in routers; no HTTP concerns in services.
- Every tenant query goes through a workspace-scoped repository. Never write an unscoped query on a tenant table.
- Validate at the edge (Pydantic) and enforce invariants in services and the DB (FK, CHECK, unique).
- Time series are append-only. Corrections create new rows. State shown to users comes from `asset_state` / latest records.
- Workflow transitions only through the workflow engine (writes history in the same transaction).
- Emit domain events from services after state changes; handlers must be idempotent.
- Errors: raise typed domain errors; never leak stack traces; problem+json.
- Logging: structlog, no PII/secrets, include request/workspace/user ids.
- Migrations: one Alembic revision per change; forward-only in shared environments; review autogenerated SQL.
- Secrets: env only; add names to `.env.example`; never commit `.env`.

## Frontend
- TypeScript strict, ESLint, Prettier; generated API types — no hand-written duplicate DTOs.
- Feature-sliced folders; shared UI in `components/`; no data fetching in presentational components.
- Every view: loading / empty / error / forbidden states.
- Strings via i18n; dates in workspace timezone; units explicit.
- Accessibility: semantic HTML, keyboard operable, non-color-only status, axe clean.
- Future features go through `CapabilityGate`; never render invented outputs.

## AI/ML honesty checklist (PR review)
- [ ] Output labelled with method (rule/statistical/model/llm)?
- [ ] Rules not described as "AI/ML"?
- [ ] Predictions carry interval/confidence + model version?
- [ ] No mock data reachable in production builds?
- [ ] Explanation/inputs stored with the recommendation?
- [ ] Human acceptance required before records are created?

## Testing
- Pure logic (rules, workflow, health bands, lifecycle) → table-driven unit tests.
- API → pytest against real PostGIS; include tenant-isolation and role tests for every new endpoint.
- Frontend → Vitest/RTL for forms and workflows; Playwright for the golden path.
- No tests written only to raise coverage.

## Git
Conventional-ish commits: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`. Small, meaningful commits. No secrets, `.env`, virtualenvs, `node_modules`, build output, local DB files. Branch from `main`, PR with description of behavior + doc updates.

## Definition of Done
Frontend + backend + database + validation + error handling + loading/empty states + tests + docs.

## Database rules for new tables and migrations
1. Create tables with Alembic (autogenerate, then review). Add PostgreSQL-only extras behind a dialect check so the same revision still runs in the SQLite unit tests.
2. Call `app.core.rls.enable_rls("<table>")` for every new table (a test fails otherwise). Never create tables in `public`.
3. History tables: `app.core.append_only.make_append_only("<table>")`; use `RESTRICT` (not `SET NULL`) for user FKs on them.
4. Tenant tables: `workspace_id` + `UNIQUE (workspace_id, id)` and composite FKs for links to other tenant tables.
5. Add an index for each real query pattern; do not add speculative ones.
6. Add every new `{ws}` route to the isolation matrix in `tests/test_tenancy.py` (a test enforces this).

## Testing modes
`TEST_DATABASE_URL` set → PostgreSQL mode (isolated schema per session, savepoint rollback per test). `GG_TEST_DB=sqlite` → fast logic mode, PostgreSQL-only tests skipped and reported. CI sets `GG_REQUIRE_POSTGRES_TESTS=1` so nothing can be skipped. New database tests must use the `world` / `pg_schema` fixtures, never open their own connection to a shared database.
