# Languages: English and Hindi (ADR-058)

## Decision: when
The foundation and the most-used screens are done now; the remaining screens are migrated progressively; **every new feature is
written with translated text from the start**. Waiting until all features exist would mean retrofitting hundreds of strings across
every screen at once, which is slow and error-prone. Doing everything now would stall product work, and part of the text (see
"Server text") needs its own design.

## How it works
- `frontend/src/i18n/`: `catalog.en.ts` is the source of every migrated string; `catalog.hi.ts` is typed against it, so **a missing
  Hindi key fails the build**. Tests check that both catalogs have the same keys and the same `{placeholders}`, that no Hindi entry is
  empty or copied from English, and that plural pairs are complete.
- `useI18n()` gives `t(key, params)`, `te(group, value)` for enumerated values (stages, roles, health bands...) with a readable
  fallback, and `fmt` for dates, numbers and relative times through the browser's `Intl` (so "3 दिन पहले" needs no catalog entry).
- Plurals: `key_one` / `key_other`, chosen by `Intl.PluralRules` for the active language.
- The language is chosen with the switcher on the sign-in page, the workspaces page and the workspace header; it is remembered in
  the browser and sets `<html lang>` for screen readers. Default: the saved choice, else Hindi if the browser prefers Hindi, else English.
- No new dependency: the layer is about 150 lines. A library (i18next) can replace it later without changing the catalogs much.
- Devanagari uses the system font (Nirmala UI on Windows; Noto on Android/Linux); no web font is loaded, so the CSP is unchanged.

## What is translated today
**Every screen the browser renders** (2026-10-22): sign-in and registration, workspaces, the workspace shell, dashboard, assets list
and asset page (observations, issues form, lifecycle, harvests, evidence, timeline), issues and issue detail, tasks, the agent page,
map, weather, members, audit log, datasets (list, detail and all its tabs, CSV import), evaluation protocols, the planned-feature
("Coming soon" / "In development") pages with their layout previews, the in-app tour, pagination, loading/empty/error states and
the not-found page. Route labels and summaries are keyed by path (`nav.route.*`, `nav.summary.*`; a test checks every route has both).

What stays English inside a Hindi interface, by design for now:
- **Server text** (next section): rule descriptions, recommendation titles, KPI reasons, dataset blockers and quality messages,
  protocol content, capability techniques and reasons, error messages.
- **Identifiers**: audit action codes (`asset.create`), rule keys, issue and task keys, SPDX licence ids, CSV column names.
- **People's own text**: asset, location and workspace names, notes, issue titles.
- The **automated browser tour** (`frontend/tour/steps.json`, run by `tour.bat`) narrates in English; the in-app tour is translated.

## Server text (not translated yet)
Some text is composed by the API: rule explanations and recommendation titles, KPI bases and reasons, validation and error messages,
capability names. It arrives in English. The plan: the API returns stable codes with parameters (most errors already carry a
`code`), the browser renders them from the catalogs, and English stays as the fallback. People's own text (names, notes, issue
titles) is never translated.

## Adding text
1. Add the English key to `catalog.en.ts`. 2. Add the Hindi key to `catalog.hi.ts` (the build fails until you do). 3. Use
`t('key')` or `te('group', value)` in the component. 4. Run `npm test`.
