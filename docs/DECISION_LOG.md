## ADR-015 · 2026-10-07 · Accepted — Hosted PostgreSQL + PostGIS (Supabase by default) for development, portable by construction

## ADR-021 · 2026-10-07 · Accepted — PostGIS tests run in a throwaway schema; connections fail fast with a diagnosis
**Context:** First real-database run failed twice for environmental reasons (password with Supabase's `[ ]` placeholder brackets; no IPv6 route to the IPv6-only direct host). The PostGIS tests also used `alembic downgrade base`, which would drop real tables if `TEST_DATABASE_URL` pointed at the dev database.
**Decision:** (1) `Settings.db_schema` (default `public`) is the first `search_path` entry; Alembic honours it for the version table; the PostGIS tests create `gg_test_<random>`, migrate inside it and `DROP SCHEMA ... CASCADE` afterwards. (2) `DB_CONNECT_TIMEOUT_S` bounds connects; `check_db` probes TCP per address family and names the cause (IPv6-only host unreachable, DNS, wrong password). (3) A bracket-wrapped password is rejected at settings load.
**Consequence:** the test suite is safe to point at any database that has PostGIS; common setup mistakes produce an actionable message instead of a hang.

## ADR-022 · 2026-10-07 · Accepted — Application tables live in a dedicated schema, never `public`
**Context:** Supabase exposes `public` through the Data API with default grants to `anon`/`authenticated`; our tables have no RLS (the backend enforces tenancy). Verified with the connector that the dedicated schema has no such grants.
**Decision:** `DB_SCHEMA` (default `greenguardian`) is the first entry of `search_path`; the migration environment creates it and keeps `alembic_version` in it; `check_db` fails if application tables appear in `public`. PostGIS stays in `extensions`. `DB_SSLMODE` (default `require`) is applied unless the URL carries its own `sslmode`.
**Also:** `TEST_DATABASE_URL` may equal `DATABASE_URL` because database tests are confined to a generated throwaway schema with a before/after canary (see DATABASE_SETUP section 5). RLS is documented as optional defence-in-depth, not applied (provider-specific; the backend role bypasses RLS).

## ADR-023 · 2026-10-07 · Accepted — RLS deny-by-default, owner/BYPASSRLS runtime role, API roles locked out
Enable RLS on every application table with no policies; revoke all schema/table/sequence/function privileges (and default privileges) from `anon`/`authenticated` where those roles exist; do not use `FORCE`. Verified facts: the backend role `postgres` owns the tables and has `BYPASSRLS`; `anon`/`authenticated` have neither. `app.core.rls` provides the helpers; a guard test and `check_db` enforce coverage. Introducing a separate non-owner runtime role later requires explicit policies in the same migration. **Consequence:** the advisor's critical "RLS disabled" finding is replaced by the intended INFO "RLS enabled, no policies".

## ADR-029 · 2026-10-07 · Accepted — Request latency is network-bound; make pre-ping configurable, colocate in deployment
Profiled before changing anything (DATABASE_SETUP section 10): 99% of request time on a remote database is round-trip waiting (~159 ms each); no N+1, ~29 ms of application time. Only measured, low-risk change: `DB_POOL_PRE_PING` setting (default true). Deployment guidance: colocate API and database. ## ADR-030 · 2026-10-07 · Accepted — Operational map: one layer registry, GeoJSON read model, Leaflet client
The map is a registry of layers over one workspace-scoped read model (`modules/map`). MVP serves one layer, `assets`, for both modes (kind distinguishes trees from crop batches; no second architecture). Filtering, scoping, viewport clipping (PostGIS `ST_Intersects` on the existing generated `centroid` columns and GiST indexes; SQLite fast mode uses lat/lon) and chip counts are computed in the database in a fixed number of statements; the browser never derives them. Future layers (disease hotspots, soil moisture, irrigation, growth, canopy, survival risk, yield) are declared in the registry as unavailable with what each requires; their endpoints return 501 and no placeholder data exists. Assets lacking coordinates are drawn at the centre of their location and flagged; assets with neither are counted as `unlocated`, not hidden silently. Client: Leaflet (small, no API key, GeoJSON-friendly) with OpenStreetMap tiles by default; the public tile server is for light use, so `VITE_MAP_TILE_URL` selects a provider for production (open item). Markers carry a glyph in addition to colour.

## ADR-031 · 2026-10-17 · Accepted — Evidence storage: object-store port, byte-verified images, authenticated retrieval
Photos are first-class evidence (the substrate for labelling and, later, disease detection) rather than URL references. Design: an `ObjectStore` protocol (`put/get/delete/exists`) with a local-disk adapter (atomic writes, key validation) and an in-memory adapter for tests, selected by `STORAGE_PROVIDER` through a registry like the weather providers; an S3-compatible adapter can be added without schema or API change (not built, no boto3 dependency yet). Table `evidence` (migration 0004, RLS on) holds provenance (uploader, time, `sha256`, dimensions) and links to the asset and optionally the observation and issue through composite tenant foreign keys. Validation never trusts the client: size cap, magic-byte sniff, Pillow header and full-decode checks, a decoded-pixel cap against decompression bombs; only JPEG/PNG/WebP. Originals are stored byte-for-byte (evidence integrity; EXIF is kept, so GPS tags in a photo are visible to workspace members). Storage keys are server-generated and never contain user input. Write order is blob then row with compensation (a failed row removes the blob; a failed blob writes nothing). Retrieval is authenticated (no public URLs); the SPA fetches the bytes with its bearer token and renders a blob URL. Deletion is soft; a purge job is future work. New dependencies: Pillow (needed later for ML preprocessing too) and python-multipart (required by FastAPI for uploads). The old `observations.attachments` JSON is kept but unused by the UI.

## ADR-032 · 2026-10-17 · Accepted — Database-backed login throttling with pair, account and address counters
Online guessing is limited by three counters (email+address 5, email 15, address 30 failures per 15 minutes; 15-minute lockout, then a fresh allowance). Alternatives: in-memory counters (lost on restart, per replica), a reverse-proxy or WAF rule (invisible to the application and to tests), CAPTCHA (hostile to field users, needs a vendor). Chosen: database rows, because they are shared by replicas, survive restarts and are testable with a controlled clock. The pair counter is much stricter than the account counter on purpose, so an attacker cannot lock a victim out from their own address. The throttle is checked before the password is verified; unknown emails throttle like real ones; the stored key is a hash. Cost: a few writes per failed login only. Limitation: a shared address with many failing users can reach the address limit (hence 30).

## ADR-033 · 2026-10-17 · Accepted — Request correlation IDs and a trusted-proxy client address
A pure-ASGI middleware owns the request context (not `BaseHTTPMiddleware`, which interferes with context propagation). Incoming IDs are accepted only in a strict pattern and never echoed otherwise (log injection, header reflection). The client address ignores `X-Forwarded-For` unless `TRUSTED_PROXY_COUNT` says how many proxies are ours, because the header is attacker-controlled. Unhandled exceptions are converted to a generic 500 inside the middleware, because Starlette's outermost handler runs after the context is cleared and would lose the ID. Also: a signing key is now mandatory outside tests (an empty `JWT_SECRET` made login crash; a short one is guessable).

## ADR-034 · 2026-10-17 · Accepted — Append-only audit trail recorded in the business transaction
Audit rows are added to the caller's session and commit with the change (atomic, no "audited but not done" or "done but not audited"). They are immutable at two layers (PostgreSQL trigger and ORM guard) and no API mutates them; the read API is manager-only and workspace-scoped. Details are scrubbed and allow-listed; failed logins keep only an email hash; attempts blocked by a lockout are not recorded (flooding). Alternatives considered: an external log pipeline (not durable or queryable per tenant yet), database triggers capturing every change (no actor or request context, noisy), event sourcing (far larger change). Not yet covered: 403 access-denied events, retention/export, a UI.

## ADR-035 · 2026-10-18 · Accepted — Audit retention through a guarded delete, not by weakening immutability
Retention conflicts with an append-only table. Options: partition by month and drop old partitions (efficient, but needs partition management and a different table shape), a SECURITY DEFINER purge function (a privileged path the application role can call), disabling the trigger during a purge (unsafe under concurrency), or never deleting. Chosen: a purpose-built trigger that permits a DELETE only in a transaction that sets a purge flag and only for rows older than a 30-day floor, with the same floor, a configurable period (default 730 days; 0 = forever) and the purge being itself audited. Partitioning remains the better answer if the table grows into the hundreds of millions of rows. Limitation: the guard stops accidents and application bugs, not an administrator with DDL rights.

## ADR-036 · 2026-10-18 · Accepted — Access-denied events recorded centrally from the 403 handler
Recording at each `raise Forbidden` would miss service-level denials and duplicate code. A single exception handler records every 403 with route template, reason, actor and workspace (identity is noted in a per-request mutable holder, because synchronous dependencies run in a thread with a copy of the context). Best-effort, non-recursive and de-duplicated per process; 401 and non-member 404 are deliberately not recorded. Trade-off: de-duplication is per process (several replicas can each record one event per window) and a denial that happens before authentication has no actor.

## ADR-039 · 2026-10-18 · Accepted — Scheduled agent: a database-polling worker whose schedule is the run history
The agent runs from `python -m app.worker` (same image as the API, separate service). Every `WORKER_POLL_INTERVAL_S` (60) it asks the database which workspaces are due and runs them one at a time. A workspace is due when its agent schedule is enabled (`workspace.settings.agent.schedule_enabled`, interval `schedule_interval_hours`, default 24) and it has never run, or its latest run succeeded at least one interval ago, or its latest run failed and the retry delay has passed (5 min, doubling per consecutive failure, never longer than the interval). There is no queue and no in-memory schedule: the schedule IS the `agent_runs` table, so a restarted worker loses nothing. Overlap is prevented by the database, not by the worker: a partial unique index allows one `running` row per workspace, and manual runs use the same claim, so a manual run, a scheduled run and a second worker can never evaluate the same workspace at once (a manual run during a scheduled one gets 409). A worker that dies leaves a `running` row; the next pass fails rows older than `AGENT_STALE_RUN_S` (1800) so the workspace is not stuck. A failing evaluation is rolled back entirely, recorded as `failed` with a short secret-redacted reason (no stack trace) and an audit event; one workspace failing never stops the others. SIGTERM/SIGINT let the run in progress finish, then exit 0. A heartbeat file backs the container health check. The same loop calls housekeeping (audit retention, throttle counters) every `HOUSEKEEPING_INTERVAL_S` (86 400). Alternatives: Celery/RQ/Arq with Redis (a new service to run, secure and back up for a job that runs once a day per workspace), APScheduler inside the API process (every replica would schedule; lost on restart), PostgreSQL `LISTEN/NOTIFY` or `pg_cron` (provider-specific, hides the logic from tests), cloud schedulers (vendor lock-in, not testable). Trade-offs: polling costs one cheap query per interval; one worker evaluates workspaces sequentially (fine into the thousands of small workspaces; add workers or shard before it is not). Limitation: the database role used by the worker can read all workspaces by design (it is the system, not a user); isolation inside a run is by `workspace_id` on every query and is tested.

## ADR-040 · 2026-10-18 · Accepted — Irrigation deferral is advisory, forecast-based and deliberately limited
`irrigation_defer` suggests that a person consider postponing a watering task that has not started and is due within the next 24 h (or up to 24 h overdue) when the forecast says at least 5 mm of rain with at least 70 % probability in the next 24 h (workspace-configurable). It is a RULE, severity low, labelled "Advisory · forecast-based". What it deliberately is not: an estimate of soil moisture or of what a plant needs. A rainfall forecast does not establish soil moisture (interception, runoff, drainage, soil type, uptake) and forecasts are wrong; the weather model's top-1-cm soil-moisture value is shown as context, marked as a coarse model estimate, and is never a trigger. Inputs it has: forecast rain, probability and temperature; the open watering task and its due date; the last completed watering; recorded symptoms and open issues. Inputs it does not have, listed in every suggestion's evidence: measured soil moisture, observed rainfall, species or crop water requirements and growth stage, soil type, irrigation method and volumes. Safeguards: withheld when the asset shows water-stress signs (wilting, scorch, a water-stress issue); silent (and counted in the run's diagnostics with a reason) when weather is unavailable, the asset has no position, the forecast is incomplete, the task has started or has no due date. Weather is requested only for assets with an open watering task (one request per ~11 km grid cell per run) and not at all when the rule is switched off. Accepting performs the one thing the person agreed to: the task's due date moves by 24 h (or to a date they choose) with a history entry; the system never reschedules or cancels work by itself. The dependency direction is unchanged (ADR-024): agent → `WeatherContextProvider` (agent's port) → `ForecastWeatherContext` → `WeatherService` → `WeatherProvider` → Open-Meteo/mock; the composition happens in `app/main.py` and `app/worker.py`, and the AST boundary test still passes. No live weather call occurs in any test (a fake provider implements the port). Not claimed: that deferring is agronomically right. Validating thresholds needs ground truth (irrigation logs, soil sensors) that does not exist yet; until it does the thresholds are conservative defaults a manager can change.

## ADR-041 · 2026-10-18 · Accepted — Recommendation lifecycle: traceable, expiring, with recorded outcomes
Each recommendation records the run that produced it (`agent_run_id`, null when evaluated inline on an observation), the rule's version (`RULE_VERSIONS`, bumped when behaviour changes) and structured evidence `{evaluated_at, rule:{key,version}, inputs:{...}}` so anyone can see exactly what the rule saw and when. Advice whose premise no longer holds becomes `expired` (never deleted, reason and run kept in the evidence): the asset was inspected, health recovered, the watering task was done, the forecast cleared. A rule that could not see the situation this time (weather unavailable, inline evaluation without a forecast) does not expire its advice. Accepting creates the operational record through the normal task/issue services, so a duplicate action is impossible (an open inspection task suppresses a new inspection suggestion; a dismissal suppresses repeats for 7 days). Follow-up: when the task or issue a recommendation led to reaches a terminal state, `outcome` (`task_completed`, `task_cancelled`, `issue_resolved`, `issue_closed`, `deferral_applied`), time and a detail line are recorded by a models-only helper called from the task/issue services (so the agent package is not imported by them). The first outcome wins; later reopening does not rewrite it (the task/issue history and audit trail hold the full story). `inspection_gap` v2 counts a completed inspection task and issue activity as attention, not only observations. Outcomes are bookkeeping for people; nothing learns from them yet (no feedback loop into thresholds exists, and none is claimed).

## ADR-042 · 2026-10-18 · Accepted — SQLite fast mode now has real transaction semantics
A test for the failure path of a run showed a rollback keeping work done before a SAVEPOINT in SQLite mode, because pysqlite's legacy transaction handling commits silently before SAVEPOINT. PostgreSQL behaved correctly (verified on the real server), so the application was right and the fast test mode was unfaithful. The SQLite engine (tests and throwaway smoke runs only) now takes over `BEGIN` using SQLAlchemy's documented recipe. The whole fast-mode suite passed unchanged with it, and CI runs the same tests on PostgreSQL. Lesson recorded: a green fast-mode test can hide a PostgreSQL difference and a red one can be a fast-mode artefact, so transactional behaviour is also verified on PostgreSQL.
